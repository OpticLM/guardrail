## 1. Core Design Philosophy

This sandbox is designed specifically for executing untrusted Bash commands and programs generated by Large Language Models (LLMs). The overall architecture strictly adheres to the following principles:

1.  **KISS (Keep It Simple, Stupid)**: Avoid heavy virtual machines and complex host directory mounting or permission restoration logic.
2.  **Default Deny**: By default, the sandbox cuts off all network access, isolates all IPC, prohibits write access to all system directories, and clears all environment variables.
3.  **Declarative API**: Sandbox policies are represented as enums. Side effects only occur collectively at the moment of spawning the child process.
4.  **Ephemeral & Stateless**: Leave no trace. Under no circumstances should permissions of existing system or user directories on the host be altered (such as NTFS ACLs). All writable operations must take place within an ephemeral "temporary workspace" that is destroyed along with the process lifecycle.

## 2. Threat Model & Confinement Dimensions

LLM-generated code is typically not malicious malware in the traditional sense, but it carries significant risks of privilege escalation, data leakage, and resource exhaustion. Our sandbox enforces comprehensive confinement across the following dimensions:

*   **File System (FS)**: No filesystem paths are granted by default. Read, write, and execute access must each be declared explicitly; access to sensitive directories is strictly prohibited unless the caller knowingly grants it.
*   **Network**: Disconnected from the network by default to prevent reverse shells or the downloading of malicious payloads.
*   **Inter-Process Communication (IPC)**: Cuts off DBus, shared memory, COM, and other channels to prevent the manipulation of other host processes.
*   **Resource Limits**: Restricts CPU time, maximum memory, and the maximum number of child processes to prevent infinite loops and fork bombs.
*   **Environment Variables (Env Scrubbing)**: Clears all inherited environment variables by default to prevent LLMs from reading and exfiltrating local secrets such as `OPENAI_API_KEY`.

## 3. Core API Design

To align with idiomatic Rust aesthetics, the external interface utilizes a Builder pattern combined with enum-driven data structures.

**Important Note:** The following is not the final code and is intended solely for demonstration to illustrate the design intent, rather than a rigid template to copy exactly.

```rust
use std::collections::HashMap;
use std::path::PathBuf;
use std::process::Command;

pub enum Policy {
    Read(PathBuf),
    Write(PathBuf),
    Execute(PathBuf),
    AllowNetwork,
    /// Enable strict IPC isolation (disables shared memory, etc.)
    StrictIpc,
}

pub struct SandboxBuilder {
    policies: Vec<Policy>,
    
    memory_limit_mb: Option<u32>,
    cpu_time_limit_sec: Option<u32>,
    max_processes: Option<u32>,
    
    env: HashMap<String, String>, 
}

impl SandboxBuilder {
    pub fn new() -> Self {
        Self { /* Initialize empty configuration */ }
    }
    
    pub fn allow_read(mut self, path: impl Into<PathBuf>) -> Self {
        self.policies.push(Policy::Read(path.into()));
        self
    }

    pub fn allow_execute(mut self, path: impl Into<PathBuf>) -> Self {
        self.policies.push(Policy::Execute(path.into()));
        self
    }
    
    pub fn memory_limit(mut self, mb: u32) -> Self { ... }
    pub fn add_env(mut self, k: &str, v: &str) -> Self { ... }
    
    /// Build and spawn the sandboxed process
    pub fn spawn(self, cmd: &mut Command) -> Result<SandboxProcess, Error> {
        // 1. Unconditional security action: Clear environment variables, inject safe whitelist
        cmd.env_clear().envs(&self.envs);
        
        // 2. Platform-specific dispatch logic
        #[cfg(target_os = "linux")]
        return linux_backend::spawn(cmd, &self);
        
        #[cfg(target_os = "windows")]
        return windows_backend::spawn(cmd, &self);
        
        #[cfg(target_os = "macos")]
        return macos_backend::spawn(cmd, &self);
    }
}
```

## 4. Backend Implementation Specs

### 4.1 Linux Backend: `landlock` + `bwrap` (+ `setrlimit`)
On Linux, we combine Seccomp-BPF and `landlock` to leverage the strengths of both:

*   **Responsibility & Mechanisms:**
    *   **Seccomp-BPF**: Used to implement network-level policies that `landlock` alone cannot handle.
    *   **`landlock` (Primary Sandboxing)**: Compiles policies directly within Rust code into a Landlock ruleset, which is then applied to the target process.
    *   **`setrlimit` (Resource Control)**: In the `pre_exec` hook of `Command`, calls the POSIX `setrlimit` API to restrict `RLIMIT_AS` (memory) and `RLIMIT_NPROC` (process count).

### 4.2 Windows Backend: AppContainer + Job Objects + Temp Workspace
We firmly avoid Windows Sandbox, instead achieving lightweight isolation by combining three native low-level Windows mechanisms:

*   **Responsibility & Mechanisms:**
    *   **AppContainer (Network & File Confinement)**: Uses Windows APIs to create an AppContainer Profile without the `internetClient` capability. The process is sandboxed inside, resulting in zero network connectivity by default. Additionally, leveraging Mandatory Integrity Control (MIC) prevents writing to other medium or high-integrity host directories.
    *   **Job Objects (Resource Control & Fail-safe Termination)**: Creates a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` configured. The sandboxed process is immediately assigned to it upon launch. Job Objects are also used to enforce CPU and memory limits.
*   **Lifecycle Guarantee**: Host process exits (or crashes) => Job Object handle is closed => All spawned processes are immediately terminated => Rust's `Drop` trait triggers, cleaning up ACL and SID artifacts. No residue remains.

### 4.3 macOS Backend (Complement): Seatbelt + `setrlimit`
*   **Responsibility & Mechanisms:**
    *   **Seatbelt (`sandbox-exec`)**: Dynamically generates a macOS Sandbox Profile using Scheme syntax at runtime based on the declared `Policy` (e.g., `(version 1) (deny default) (allow file-read* ...)`). Executes the target command wrapped with `sandbox-exec -p <profile>`.
    *   **`setrlimit`**: Identical to Linux, handling memory and process count restrictions.

## 5. Core Policy

### 5.1 File System
*   No directories can be read or written by default.
*   Grant read permissions to a specific directory or file.
*   Grant write permissions to a specific directory or file.
*   Grant execute permissions to a specific directory or file.

### 5.2 Network
*   No network connections allowed by default.
*   Allow outgoing connections (by default, binding and listening remain prohibited unless explicitly configured).
*   Allow binding/listening.
*   (Windows-specific, No-op on other platforms) Allow loopback connections.

### 5.3 IPC
*   We do not need to concern ourselves with Linux DBus, as that is governed by file system policies.
*   No IPC allowed by default. Pay special attention to using `seccomp` on Linux to disable shared memory, message queues, and `ptrace`.
*   Recommended IPC levels: Use a built-in Seatbelt preset on macOS; allow essential mechanisms like pipes, `socketpair`, shared memory, and anonymous file mappings on Linux; no special operations are required on Windows.

## 6. Observability

When a program inside the sandbox is terminated or errors out due to a policy violation, the sandbox must provide actionable feedback to the creator, explicitly indicating which policy rule needs to be added to resolve the issue. This simplifies debugging.

## 7. Unit Tests

Unit tests **must not** simply mirror the internal implementation details of the code. Repeating the exact sequence of known execution steps in a unit test and asserting it works is not a true verification. Instead, tests **must** validate the high-level intent of the code. This approach minimizes redundant and unnecessary tests, ensuring that the code's behavior aligns with your original design intent rather than merely asserting that the code executes what it was written to execute.
