## The direction these plans serve

Guardrail is a sandbox for LLM agents: rarely malicious, often accidentally
destructive, unpredictable. The maintainer chose one direction from the
audit — **denial observability** — with a deliberately minimal shape:

- Guardrail does not collect, parse, or expose logs. No log-fetching API.
- Each operating system already has a native log. Guardrail only leaves
  markers there so operators can filter and attribute denials with their own
  tools. Operators are assumed to have full access to the machine.

| Platform | Marker | Always on? |
|---|---|---|
| macOS | `(with message "guardrail:fs[N]")` / `"guardrail:default"` on every generated Seatbelt deny rule | yes |
| Linux | `personality(2)` value `0x3000000` on the sandboxed process tree, shown as `per=` in syscall audit records and matchable by an audit rule. A seccomp rule pins it, so the tree cannot clear it | opt-in (`linux_audit_denials`); silent until the host installs audit rules |
| Linux | Landlock and seccomp record their own denials | opt-in (the same `linux_audit_denials`) |
| Windows | — | deferred |

## Dependency notes

- 001 needs a macOS host. 002 and 003 need a Linux host where
  `cargo test -p guardrail-linux --all-targets` passes at baseline (the
  backend needs unprivileged user + mount + IPC namespaces and an existing
  `/dev/mqueue` directory; the container these plans were written in lacks
  the directory until `mkdir /dev/mqueue` is run as root — see plan 002's
  "Host requirement").
- Plan 002 was implemented on 2026-11-16, including its live audit-daemon
  step. Plan 003's code blocks have not been built or run.
- Two host traps found while running the Linux suite. The tests that call
  `common::landlock_enforced()` read `/sys/kernel/security/lsm` and skip
  silently when securityfs is not mounted
  (`mount -t securityfs securityfs /sys/kernel/security`). And
  `filesystem::read_allow_then_read_deny_denies_child_but_allows_sibling`
  fails when the suite runs as root; see "Known gaps".
- 003 depends on 002 in code. 002 adds `SandboxConfig::linux_audit_denials`
  and threads it through the Linux backend and the Node binding; 003 adds
  the kernel logging flags under the same field.
- 002 adds a `SandboxConfig` field, which touches every exhaustive config
  literal in the macOS and Windows crates. Those edits are compile-checked
  only by CI on their own runners.

## Decisions recorded

- **Linux self-logging is opt-in** via one boolean (plan 003). Maintainer
  decision, 2026-11-14.
- **No host-supplied label in the markers** for now. Deferred by the
  maintainer; if added later, append it to the macOS message text.
- **The Linux process marker is opt-in, pinned, and mandatory once opted
  in** (plan 002), under the same `linux_audit_denials` boolean as the
  self-logging. Maintainer decision, 2026-11-15. It replaces the earlier
  recommendation of an always-on, best-effort marker, which had two
  drawbacks:
  - A sandboxed process could clear it. This happens by accident too:
    `setarch` overwrites the whole personality word, so `setarch -R cmd`
    dropped the marker. Now a seccomp rule refuses every `personality(2)`
    call that would drop a marker bit.
  - A host that refuses `personality(2)` silently produced unmarked
    sandboxes. Now `LinuxBackend::new` fails with `Error::Unsupported` on
    such a host, and a spawn fails rather than run unmarked.

  Accepted costs: inside an opted-in sandbox, `setarch`, `linux32` and
  similar tools fail with `EPERM`; a host that locks personality (systemd
  `LockPersonality=`, Docker's default seccomp profile) cannot opt in. With
  the option off, nothing is marked and nothing is pinned.
- **Personality stays the marker.** Checked against kernel v6.18 on
  2026-11-15: the audit rule fields that describe a process are its user and
  group ids, login session, security label, executable, pid, parent pid, and
  personality. There is no field for namespaces, cgroups, seccomp state, or
  Landlock domains. Personality is the only one an unprivileged process can
  set, so the marker's weaknesses are fixed around it rather than by
  replacing it.

## Known gaps after all three plans

- Linux: a lookup inside a read-denied directory that has a re-allowed
  descendant returns `ENOENT`, which no errno-keyed audit rule can tell from
  an honest miss.
- Linux: kernel records cannot carry free text, so the rule index is not in
  the log. Attribution is by joining the logged path against the policy.
- Linux: inside an opted-in sandbox, tools that rewrite the personality word
  without the marker bits (`setarch`, `linux32`) fail with `EPERM`.
- Linux: a host that refuses `personality(2)` cannot opt in. An operator
  there can still filter syscall audit records by the uid the agent runs as,
  which also matches the host application's own failures.
- Linux: a sandboxed process can keep a denial out of the Landlock or
  seccomp records by stacking its own Landlock domain or seccomp filter that
  denies the same access with logging off, because the kernel takes the
  logging decision from the newest layer that denies. The access is denied
  either way, so the process gains nothing and learns nothing about
  guardrail's policy.
- Linux, host running as root: a read-denied file or directory beneath an
  allowed parent is hidden, not refused. The sandboxed process keeps
  `CAP_DAC_OVERRIDE` inside its user namespace, so opening the mode-0 mask
  succeeds and yields an empty file or directory. The content does not leak,
  but no errno is returned, so no errno-keyed audit rule records the attempt.
  This predates these plans (checked on `a5c8219`, 2026-11-16) and is not
  addressed by them.
- Linux: the audit queue drops records under load, so counts are a lower
  bound, and a process can provoke that deliberately. Queue size and
  overflow behavior are host audit settings.
- Windows: nothing. See below.

## Findings considered and rejected

- **Staged writes (overlay / transactional runs)**: rejected by the
  maintainer — virtualization belongs to a separate project; guardrail stays
  a lightweight sandbox.
- **Private process world (PID namespace, tree-wide budgets)**: rejected for
  the same reason.
- **Soft tripwires (seccomp user-notification on destructive syscalls)**:
  rejected for the same reason.
- **Windows denial auditing**: deferred entirely by the maintainer. Native
  failure auditing needs an audit entry in each object's SACL, which the
  unprivileged library cannot write; whether events quote guardrail's
  per-namespace SIDs for an AppContainer child was never verified.
- **A denial event/observer API or log reader in guardrail**: rejected — the
  design is markers only; operators retrieve logs.
- **Policy self-description for the agent's prompt, and one-rule patch
  suggestions**: dropped from the observability direction to keep it minimal.
- **A shared pure policy evaluator in core (`(path, right) → rule index`)**:
  not planned. It would give uniform rule attribution on Linux, and the same
  last-rule-wins function exists privately in
  `crates/guardrail-linux/src/fs.rs` and `crates/guardrail-windows/src/acl.rs`;
  left as an optional follow-up for the maintainer to request.
- **Making Landlock itself log mount-mask denials**: not possible. Landlock
  grants are additive and inherited down the hierarchy through mount points,
  so a denial beneath an allowed parent is never a Landlock denial. Upstream
  Linux has no "do not inherit" rule flag as of this writing: mainline is at
  Landlock ABI 12 without one, and a `LANDLOCK_ADD_RULE_NO_INHERIT` patch
  series was still under review in 2026. If it lands, deny-under-allow rules
  can become Landlock rules, every filesystem denial is then logged natively
  with an unforgeable domain id, and the process marker can be retired.
- **A shared sentinel inode for read-deny masks (one audit watch)**: weaker
  than the process marker — it misses write and execute denies and deep
  lookups.
- **A different unprivileged process marker**: none exists; see "Personality
  stays the marker" above. The attributes an audit rule can also match
  (supplementary group, login session, security label) all need privilege
  or host setup to assign. A privileged variant is an open question and not
  part of these plans.
- **Letting a marker-clearing `personality(2)` call through and only logging
  it** (seccomp `SECCOMP_RET_LOG`): keeps `setarch` working but makes
  clearing visible instead of impossible. Not chosen.
- **Per-tool policy presets** (cargo, pnpm, go profiles): not proposed — it
  treats the symptom of unpredictable tool writes and hides overreach behind
  a friendly name.
- **Domain-allowlist network proxy**: not proposed — it needs a proxy
  process, which is glue against the repo's KISS rule.
- **Splitting write into create / modify / delete rights**: not proposed —
  editors' atomic saves need delete rights, so it cannot express "do not
  destroy existing content".
- **Observe mode that generates a policy**: not proposed — it needs
  privileged tracing on two of the three platforms.
- **README inconsistency** (`crates/guardrail-napi/README.md:1107` says
  Windows ACEs are not removed when a sandbox exits; `:1175` says they are):
  noted, not planned — out of the chosen direction.
