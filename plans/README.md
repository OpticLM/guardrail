# Implementation Plans — `guardrail`

Generated by the `improve` skill on 2026-06-21, against commit `a1d2a66` and
`spec.md`. Plans 001-006 implement the **`guardrail-core`** crate
(platform-agnostic interfaces) and the **`guardrail-linux`** crate (the Linux
backend), from a greenfield `cargo new` skeleton. Plans 007-010 extend the work
to the **Windows backend**, planned against commit `44fcf4e0`.

Each executor: **read the plan fully before starting**, run every verification
command, honor the plan's STOP conditions, and update your row below when done.
Do **not** commit/branch/push — this repo uses **jj (Jujutsu)** colocated with
git; leave changes in the working copy for the operator to review.

## Decisions baked into these plans (from the operator)

- **Pure in-process Linux confinement**: Landlock + seccomp-BPF + `setrlimit`,
  all applied via `Command::pre_exec`. **No bubblewrap**, no namespaces, no
  external binary (resolves the `spec.md` §4.1 heading-vs-body ambiguity in
  favor of the body + §1 KISS).
- **No ephemeral temp workspace**: the `spec.md` §1.4 "ephemeral workspace
  destroyed with the process" idea is dropped for now. Filesystem access is only
  the explicit `Read`/`Write`/`Execute` grants. The Linux backend must not add
  builtin grants for system directories or for the target binary.
- **Single seccomp denylist, `match_action = Trap` (SIGSYS)** so violations are
  observable by the parent (`spec.md` §6). Centralized in one constant; switching
  to graceful `Errno` is a one-line change later.
- **`guardrail-probe` helper binary** drives all Linux integration tests
  deterministically (no dependence on `curl`/network/system tools).
- Scope for plans 001-006 was **`guardrail-core` + `guardrail-linux` only**.
  Plans 007-010 add **`guardrail-windows`**. macOS and a top-level `guardrail`
  facade crate remain out of scope.
- **Windows filesystem grants use temporary AppContainer ACL entries** for the
  explicit `FsAccess` paths only, then restore the original descriptors. This
  follows `spec.md` section 4.2's "cleaning up ACL and SID artifacts" note; it
  is narrower than changing broad host permissions, but it is still a deliberate
  Windows-specific tradeoff.
- **Current Windows baseline before plan 007**: `cargo test -p guardrail-core`
  passes, but `cargo test --workspace` fails on Windows because
  `guardrail-linux` is an unconditional workspace member and `seccompiler`
  imports Linux-only `libc` symbols. Plan 007 fixes the target gating.

## Dependency graph

```
001 (core API)
 └─ 002 (linux skeleton: LinuxBackend, pre_exec, setrlimit, env, guardrail-probe)
     ├─ 003 (Landlock FS)            ── independent of 004/005 ─┐
     └─ 004 (seccomp network)                                   │
         └─ 005 (seccomp IPC, extends 004's seccomp.rs)         │
                                                                │
              006 (diagnostics) ◄── needs 002+004+005, uses 003 signals
```

- **001 is the foundation** — every other plan consumes its `Backend` trait,
  `SandboxConfig`, policy enums, `Error`, and `SandboxChild`. Do it first.
- **002 before 003/004** — both insert into the `pre_exec` hook and use the
  `guardrail-probe` test helper that 002 creates.
- **003 and 004 are independent** of each other; they can be executed in either
  order (or in parallel by two executors) once 002 lands.
- **005 extends 004's `seccomp.rs`** (adds IPC rules to the same filter) — 004 first.
- **006 last** — it interprets the SIGSYS/SIGXCPU/SIGKILL signals that 004/005/002
  produce and the silent FS denials from 003; its tests need real confinement.

A reasonable single-threaded order for Linux is simply **001 → 002 → 003 → 004 → 005 → 006**.
For Windows, execute **007 → 008 → 009 → 010**. Do not start 009 until 008 has
a working suspended/raw process launch path and `SandboxChild` owns the Windows
process/job handles; AppContainer needs extended startup attributes and cannot
be bolted onto an already-running `std::process::Child`.

## Verification gates (every plan)

All plans share these repo-wide gates (exact commands in each plan):

- `cargo build` / `cargo test` for the relevant crate, **exit 0**
- `cargo clippy ... -- -D warnings`, **exit 0**
- `cargo fmt --check`, **exit 0**
- On Windows after plan 007, `cargo test --workspace` must no longer try to
  compile Linux-only seccomp/Landlock code for the Windows target.
- Tests assert **high-level intent** per `spec.md` §7 — they exercise observable
  behavior (does the syscall fail? is the var cleared?), not the internal
  sequence of confinement calls.

Toolchain confirmed during recon: `rustc`/`cargo` 1.95, edition 2024; kernel
`7.0.8` (Landlock ABI v7 and seccomp both available, so tests enforce for real
locally). Crate choices: `landlock` 0.4, `seccompiler` 0.5, `libc` 0.2,
`thiserror` 2, `tempfile` 3 (dev).

## Notes / deferred items (not bugs — intentional scope cuts)

- **Ephemeral temp workspace** (`spec.md` §1.4): dropped per operator decision.
  Revisit only if the explicit-grant model proves insufficient.
- **macOS backend** (`spec.md` §4.3): still out of scope. The
  `guardrail_core::Backend` trait is the seam it would implement.
- **Top-level `guardrail` facade** with cfg-dispatched `SandboxBuilder::spawn`
  (as sketched in `spec.md` §3): out of scope. For now callers wire a backend
  explicitly: `config.spawn_with(&LinuxBackend::new(), cmd)`.
- **Precise violation attribution** (exact denied syscall via seccomp
  user-notification; exact denied path via Landlock ABI-v7 audit log): deferred
  in plan 006 as a large follow-up. Current diagnostics are heuristic.
- **`RLIMIT_NPROC` test** is `#[ignore]`d (plan 002) because the limit is
  per-real-uid system-wide and flaky in shared/CI environments.
- **Architecture coverage** for seccomp is x86_64/aarch64/riscv64 (direct socket
  syscalls; not i386 `socketcall` or SysV `ipc` multiplexers). Plans 004/005
  STOP and report on unsupported arches rather than silently under-confining.
- **Landlock self-exec requirement** (discovered executing plan 003): once
  filesystem confinement is active, a sandboxed process cannot `execve` its own
  binary unless execute is granted on the binary's location, and dynamic
  programs also need explicit read/execute grants for their loader and shared
  libraries. Tests now grant these paths explicitly through their helper rather
  than relying on hidden `LinuxBackend` defaults.
