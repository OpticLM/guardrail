## The direction these plans serve

Guardrail is a sandbox for LLM agents: rarely malicious, often accidentally
destructive, unpredictable. The maintainer chose one direction from the
audit — **denial observability** — with a deliberately minimal shape:

- Guardrail does not collect, parse, or expose logs. No log-fetching API.
- Each operating system already has a native log. Guardrail only leaves
  markers there so operators can filter and attribute denials with their own
  tools. Operators are assumed to have full access to the machine.

| Platform | Marker | Always on? |
|---|---|---|
| macOS | `(with message "guardrail:fs[N]")` / `"guardrail:default"` on every generated Seatbelt deny rule | yes |
| Linux | `personality(2)` value `0x3000000` on the sandboxed process tree, shown as `per=` in syscall audit records and matchable by an audit rule | yes (silent until the host installs audit rules) |
| Linux | Landlock and seccomp record their own denials | opt-in (`linux_audit_denials`) |
| Windows | — | deferred |

## Dependency notes

- 001 needs a macOS host. 002 and 003 need a Linux host where
  `cargo test -p guardrail-linux --all-targets` passes at baseline (the
  backend needs unprivileged user + mount + IPC namespaces; the container
  these plans were written in cannot provide them).
- 003 follows 002 only because both edit the `pre_exec` closure in
  `crates/guardrail-linux/src/backend.rs` and the README's
  `## Auditing Denials` section. There is no code dependency.
- 003 adds a `SandboxConfig` field, which touches every exhaustive config
  literal in the macOS and Windows crates. Those edits are compile-checked
  only by CI on their own runners.

## Decisions recorded

- **Linux self-logging is opt-in** via one boolean (plan 003). Maintainer
  decision, 2026-11-14.
- **No host-supplied label in the markers** for now. Deferred by the
  maintainer; if added later, append it to the macOS message text.
- **The Linux process marker is always on, best-effort, with no config
  field** (plan 002). This is the advisor's recommendation, not yet confirmed
  by the maintainer. It reuses two `personality(2)` flags the kernel defines
  but never reads; reject plan 002 if that is unacceptable.

## Known gaps after all three plans

- Linux: a lookup inside a read-denied directory that has a re-allowed
  descendant returns `ENOENT`, which no errno-keyed audit rule can tell from
  an honest miss.
- Linux: kernel records cannot carry free text, so the rule index is not in
  the log. Attribution is by joining the logged path against the policy.
- Linux: the process marker is not tamper-proof; a sandboxed process can
  clear it. It is for statistics and accidents, not a security boundary.
- Windows: nothing. See below.

## What was not audited

This was a direction-only pass (the skill's `next` variant). Correctness,
security, performance, test coverage, tech debt, dependencies, and DX were
not audited.

## Findings considered and rejected

- **Staged writes (overlay / transactional runs)**: rejected by the
  maintainer — virtualization belongs to a separate project; guardrail stays
  a lightweight sandbox.
- **Private process world (PID namespace, tree-wide budgets)**: rejected for
  the same reason.
- **Soft tripwires (seccomp user-notification on destructive syscalls)**:
  rejected for the same reason.
- **Windows denial auditing**: deferred entirely by the maintainer. Native
  failure auditing needs an audit entry in each object's SACL, which the
  unprivileged library cannot write; whether events quote guardrail's
  per-namespace SIDs for an AppContainer child was never verified.
- **A denial event/observer API or log reader in guardrail**: rejected — the
  design is markers only; operators retrieve logs.
- **Policy self-description for the agent's prompt, and one-rule patch
  suggestions**: dropped from the observability direction to keep it minimal.
- **A shared pure policy evaluator in core (`(path, right) → rule index`)**:
  not planned. It would give uniform rule attribution on Linux, and the same
  last-rule-wins function exists privately in
  `crates/guardrail-linux/src/fs.rs` and `crates/guardrail-windows/src/acl.rs`;
  left as an optional follow-up for the maintainer to request.
- **Making Landlock itself log mount-mask denials**: not possible. Landlock
  grants are additive and inherited down the hierarchy through mount points,
  so a denial beneath an allowed parent is never a Landlock denial. Upstream
  Linux has no "do not inherit" rule flag as of this writing.
- **A shared sentinel inode for read-deny masks (one audit watch)**: weaker
  than the process marker — it misses write and execute denies and deep
  lookups.
- **Per-tool policy presets** (cargo, pnpm, go profiles): not proposed — it
  treats the symptom of unpredictable tool writes and hides overreach behind
  a friendly name.
- **Domain-allowlist network proxy**: not proposed — it needs a proxy
  process, which is glue against the repo's KISS rule.
- **Splitting write into create / modify / delete rights**: not proposed —
  editors' atomic saves need delete rights, so it cannot express "do not
  destroy existing content".
- **Observe mode that generates a policy**: not proposed — it needs
  privileged tracing on two of the three platforms.
- **README inconsistency** (`crates/guardrail-napi/README.md:1107` says
  Windows ACEs are not removed when a sandbox exits; `:1175` says they are):
  noted, not planned — out of the chosen direction.
